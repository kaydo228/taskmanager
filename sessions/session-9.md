## Размышления

Фраза «редактор текста» неоднозначна: это может быть визуально улучшенное многострочное поле, Markdown-редактор или WYSIWYG с форматированием. Сначала нужно проверить текущий TaskForm, тип `description`, способ хранения и отображения карточки. Выбор нельзя делать вслепую: WYSIWYG затрагивает формат данных и безопасность вывода, а новые пакеты запрещены без согласования.

Исследование показало: `TaskForm` регистрирует обычную `textarea` через React Hook Form, `description` хранится как строка в существующем массиве localStorage и выводится в карточке как безопасный текстовый `<p>`. Специализированной editor-зависимости нет. Значит, редактор можно добавить без изменения схемы только если явно выбрать формат строки и способ отображения; HTML-путь потребует санитизации и несёт лишний риск.

Пользователь выбрал расширенный редактор с заголовками, цитатами, кодом, списками и ссылками. Для такого объёма самописный `contentEditable` будет хрупким: придётся самостоятельно решать выделение, историю команд, вставку и санитизацию. Следующее обязательное решение — разрешена ли специализированная зависимость, поскольку правила проекта запрещают добавлять пакеты без отдельного согласования.

Пользователь разрешил зависимость. По официальной документации рассматриваются три реальных направления: `@uiw/react-md-editor` даёт toolbar и live Markdown preview одним пакетом и сохраняет строковый контракт; Tiptap даёт прямой WYSIWYG, но требует минимум три пакета и отдельный формат документа; Lexical гибок, но требует собственной сборки toolbar/plugins. Выбор между Markdown split-view и WYSIWYG визуально существенен, поэтому перед финальным предложением уместно предложить наглядное сравнение.

Пользователь отказался от визуального сравнения, поэтому подходы будут согласованы текстом. Рекомендуемый вариант — Markdown editor: он единственный одновременно даёт расширенные возможности, требует одну прямую зависимость и оставляет `description: string` совместимым со старыми задачами. WYSIWYG-варианты дороже по пакетам и миграции данных.

Пользователь всё же выбрал второй вариант — Tiptap WYSIWYG. Это осознанный обмен: интерфейс редактирования будет привычнее и сразу покажет итоговое форматирование, но потребуются согласованные Tiptap-пакеты и сериализация JSON-документа. Чтобы не менять источник данных и Zod-схему задачи, документ будет храниться внутри прежней строки `description` с однозначным префиксом; старый обычный текст останется валидным и будет преобразовываться в абзац только при чтении редактором.

Пользователь утвердил архитектуру хранения: четыре прямые Tiptap-зависимости, JSON-документ внутри существующей строки с префиксом, совместимость со старыми текстовыми описаниями, пустая строка для пустого документа и безопасный React-рендеринг карточки без HTML-инъекции.

Пользователь утвердил интерфейс: расширенная панель форматирования, собственный ввод ссылки с проверкой протокола, SVG-иконки, адаптивный перенос toolbar, фокус-стили, клавиатурное управление и компактное отображение форматирования внутри карточки.

Пользователь утвердил поток данных и проверки: интеграцию через `Controller`, сериализацию при изменении, ленивую совместимость со старыми задачами, безопасный статический вывод, локальную обработку ошибок ссылки и тесты создания/редактирования/перезагрузки. Дизайн записан отдельно до правок кода. При самопроверке сохранена граница задачи: localStorage и Zod-схема не меняются, изображения, таблицы и серверное хранение исключены.

Пользователь просмотрел записанную дизайн-спецификацию и подтвердил переход к реализации. Перед кодом составляется отдельный пошаговый TDD-план; версии Tiptap проверены в npm и будут одинаково закреплены на `3.30.1`.

План разбит по проверяемым границам: кодек, редактор, React Hook Form, карточка, стили/e2e и финальная приёмка. При самопроверке обнаружены и исправлены две ошибки плана: ожидание лишнего второго аргумента `onSubmit` могло сделать тест хрупким, а константа расширений статического рендера сначала использовалась без точного определения. Проверка на запрещённые заглушки прошла, Prettier применён к новым Markdown-файлам.
